# Admission Hub v0.16.4 — v0.9.12 Auth Baseline Restore

v0.16.4는 최신 로그인 상태기계를 계속 덧붙이는 대신, 실제 Galaxy에서 진학사 인증과 수집이 확인됐던 과거 흐름을 기준선으로 되돌려 회귀를 제거하는 버전입니다.

## 실기기 비교 기준

가장 강한 비교 기준은 v0.9.12입니다.

- v0.9.11 실기기 export에서 진학사 인증 성공이 확인됨
- v0.9.12 실기기에서 attemptedSnapshots 66 / successfulSnapshots 65
- Jinhak records 145
- analysis capture 15
- application identities 30
- mission targets 30
- bootstrap fatal 0

또한 v0.8.5 실기기에서는 Jinhak records 4,061 / completed documents 410 / prediction-report 5 / score-calc-report 9까지 수집됐습니다. 즉 현재 문제는 진학사 자체 접근 불가가 아니라 이후 추가된 인증/grade-product 상태기계의 회귀로 판단합니다.

## 비교 결과

v0.9.12 로그인 흐름:

1. provider home/session 상태 확인
2. 실제 렌더링된 로그인 form이 보일 때만 자격정보 자동 입력
3. Jinhak 자체 redirect/landing을 막지 않음
4. 로그인 이후 protected high3 core에서 인증 증거 확인
5. 인증되면 보존된 batch target으로 복귀

v0.16.1~v0.16.3에서 추가된 흐름:

- 로그인 DOM에서 고3·N수 product tab을 JavaScript로 클릭
- 고1·2 product 상태를 auth failure/recovery signal로 사용
- lower-grade URL/DOM을 startup auth 단계에서도 차단
- 별도 lower-grade manual gate / bounded recovery가 auth state ownership을 가져감

실기기 화면에서는 고1·2 차단 자체는 동작했지만 `로그인 확인 중 / 수집 대기`에 고정됐습니다. 따라서 차단 로직이 실제 Jinhak 인증 redirect보다 먼저 개입한 것이 핵심 회귀 후보입니다.

## v0.16.4 변경

### 1. 인증 중에는 v0.9.12 방식 우선

`jinhakAuthCompatibilityWindowActive`를 추가했습니다.

다음 상태에서는 Jinhak의 실제 인증 redirect를 먼저 완료시킵니다.

- startup login preflight
- transition auth gate
- real auth probe
- batch login pause
- credential submit 후 login-exit 대기
- Jinhak unified phase에서 protected core 미검증 상태

이 auth window에서는 lower-grade route를 collection navigation처럼 즉시 차단하지 않습니다.

### 2. 고1·2는 사용자에게 표시하지 않음

인증 중 lower-grade/member transition은 WebView를 숨긴 상태로 통과시킵니다.

공용 로그인 페이지가 렌더링되면 고1·2 선택 UI만 CSS/DOM 이벤트로 숨기고 클릭을 차단합니다.

중요: 더 이상 JavaScript로 고3·N수 탭을 클릭해 Jinhak product state를 변경하지 않습니다.

### 3. 자동 로그인은 v0.9.12 passive semantics

새 `attemptSavedCredentialLoginV0912Baseline` 경로는:

- visible password/user form 탐지
- iframe/shadow root 접근 가능한 범위 탐지
- 실제 form/button submit
- 900ms 기본 throttle / 6초 in-flight 보호
- product tab 사전 클릭 없음

으로 동작합니다.

### 4. 인증 후 protected high3 core가 유일한 승격 기준

일반 member/고1·2 landing에서 세션이 인증됐더라도 곧바로 Jinhak 수집 인증 성공으로 승격하지 않습니다.

반드시 `JinhakGradeRouteFence.isHigh3(url)`인 protected high3 route에서 세션이 실제 authenticated 상태여야:

- `jinhakAuthVerifiedForBatch=true`
- `resumeBatchAfterVerifiedJinhakAuth(...)`
- 또는 Jinhak `startBatch()`

를 실행합니다.

### 5. 인증 완료 후에는 grade fence 복원

v0.9.12 auth compatibility window가 끝나면 기존 high3 collection fence가 다시 활성화됩니다.

따라서 실제 수집 도중 고1/high2/high12 route로 새는 것은 계속 차단합니다.

## 신규 실기기 진단값

다음 export에서 아래 값을 확인할 수 있습니다.

- `jinhakV0912AuthCompatibilityTransitions`
- `jinhakV0912PassiveLoginSubmissions`
- `jinhakV0912ProtectedCoreHandoffs`
- `jinhakV0912ProtectedCoreVerified`

실기기 승인 최소 조건:

1. `jinhakV0912PassiveLoginSubmissions >= 1` 또는 기존 인증 세션 재사용
2. `jinhakV0912ProtectedCoreVerified >= 1`
3. `jinhakBatchStartCount >= 1`
4. Jinhak successfulSnapshots / records / analysis 중 하나 이상 증가
5. 5분 이상 `로그인 확인 중 / 수집 대기` 고착 없음
6. 고1·2 UI가 사용자 화면에 지속 노출되지 않음
7. credential/cookie/token/form value export 없음

## 입시 데이터 정책

- 어디가/대학 입학처: 공식 기준 및 공식 과거 입결
- 진학사: 사용자 계정에서 실제 열람한 예측·분석
- 진학사 값을 공식 입결로 승격하지 않음
- 사용자 고정 6장 자동 변경 없음
- `HOLD` / `probabilityInferred=false`에서 합격확률을 생성하지 않음

CI 성공은 실제 Galaxy 로그인 성공을 대신하지 않습니다. 이 릴리스의 최종 승인 여부는 위 실기기 조건으로 판단합니다.
