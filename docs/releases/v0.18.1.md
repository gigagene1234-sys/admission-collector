# Admission Hub v0.18.1 — Focused Six Missions

v0.18.1 changes the Jinhak collector from an open-world high3 crawler into a six-application mission collector when six Hub slots are pinned.

## Why this release exists

The v0.18.0 real-device export proved that the WebView could read Jinhak after login (2,276 Jinhak records and 611/611 successful snapshots), but the crawler spent most of its time on strategy/knowledge content while zero application mission actions were executed. The newest graph collapsed to one unrelated candidate even though a reusable 27-candidate graph and six pinned applications were still available locally.

## Focused collection

- Six occupied Hub slots seed the Jinhak expected identity set before the batch starts.
- Jinhak collection boots on the protected saved-application surface, not on whichever generic high3 page the login router returns.
- The automatic frontier is limited to saved applications, current prediction, mock support, actual admits, score analysis, and university results.
- Strategy, admission knowledge, editorial, media, curation, recommendation, generic reference, and unknown routes are not autonomous selected-six targets.
- Generic agent fallback is disabled while six pinned applications are active.
- Default Jinhak seeds are reduced to saved applications and current prediction; strategy and broad university-search seeds are removed.

## Login stabilization

- The dedicated v0.18.0 auth WebView remains separate from the collector WebView.
- Credential values remain device-only in the Android Keystore-backed CredentialVault.
- Form discovery remains bounded, but the hydration window increases from 3 to 12 attempts so the current rendered Jinhak login form has time to expose its fields.
- Successful authentication hands the collector to the protected saved-application route.
- Manual login remains a fallback if the form cannot be automated.

## Local continuity and dashboard

- Pinned identity keys remain authoritative even when the newest candidate graph is stale.
- Score summary materialization now prefers current-session canonical rows but falls back to the newest reusable canonical row for each pinned identity.
- A stale Hub card remains HOLD/unresolvable, but verified conversion/outcome evidence attached to that pinned identity is no longer hidden from the dashboard.
- No stale identity is silently promoted to a resolved current candidate.

## Evidence policy

- Adiga/university evidence remains the official layer.
- Jinhak remains user-viewed derived analysis/prediction and is never promoted to official evidence.
- This release does not infer admission probability; HOLD/probabilityInferred rules are unchanged.
- Credentials, cookies, session secrets, and form values are not exported.

## Acceptance target

On a real device with six pinned applications, the expected path is: authenticate (automatically if the device vault and rendered form allow it) → protected saved-applications → application-bound report missions. Strategy/knowledge article traversal should not dominate or loop the batch. The six pinned identity set should remain the expected mission scope even if the newest canonical graph is stale.
