# Admission Hub v0.18.3 — Storage Competition Watch

v0.18.3 deliberately reduces the Jinhak collection surface to the protected Susi saved-application repository (`/jh/high3/early/four-year-university/library`). The goal is to reduce login/session/navigation failure points and add a conservative competition-rate watch for saved applications.

## Jinhak scope
- Jinhak batch seeds contain only the protected Susi saved-application repository.
- Report pages, recommendation pages, editorial pages, generic frontier routes, and same-card report actions are not traversed in this release.
- Login is still required when Jinhak requires it; this release does not claim to eliminate provider authentication.
- After protected storage access is verified, the same storage page is refreshed every 15 minutes while the watch run remains active in the app.

## Competition evidence
- Competition observations are bound only to the same saved-application card identity.
- Explicit labels such as `현재 경쟁률`, `실시간 경쟁률`, `원서접수 경쟁률`, or `접수 경쟁률` may populate `currentApplicationCompetition`.
- An unlabeled visible `경쟁률` may be preserved as `displayedCompetition`, but is not promoted to current competition.
- `모의지원 경쟁률`, previous-year competition, and historical competition are not treated as current application competition.
- Applicant count / capacity is never converted into a competition rate by inference.
- Every watch observation preserves `observedAt` so changes can be reconstructed as a time series.

## Evidence policy
- Adiga/university evidence remains official.
- Jinhak competition observations remain user-viewed derived evidence.
- Jinhak is never promoted to official evidence.
- HOLD and `probabilityInferred=false` behavior is unchanged.
- No acceptance probability or 안정/적정/소신 label is created from competition data.
- Credentials, cookies, form values, and session secrets are not exported.

## Runtime boundary
The first v0.18.3 build validates source contracts, unit tests, signing, and packaging. Real Galaxy acceptance remains required before claiming that the provider-side login problem is solved.
