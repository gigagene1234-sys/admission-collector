# Admission Hub v0.18.0 — Dedicated Auto Login

v0.18.0 replaces the accumulated Jinhak authentication handoff logic with a separate authentication WebView and a deterministic one-shot/bounded state machine.

## Architecture

- The **collector WebView remains high3-only**. It never loads the generic Jinhak login page.
- A separate **auth WebView** owns login UI and shares the native WebView cookie jar with the collector.
- The current unified login page `https://www.jinhak.com/jh/member/login` is the primary auth entry.
- The legacy `member.jinhak.com/.../MemberLogIn.aspx` surface is accepted only inside the auth WebView when the site uses it.
- high1/high2/high12 remain blocked in both auth and collector contexts, including encoded forms.
- After the auth WebView reaches a valid high3 URL, the collector is marked authenticated and receives only a high3 destination.

## Automatic login

- Jinhak credentials can again be saved explicitly by the user in the existing Android-Keystore AES/GCM `CredentialVault`.
- After that one-time device setup, login is filled and submitted automatically when the Jinhak login surface is reached.
- Form discovery is bounded to three attempts. There is no recursive auth poll loop.
- A submitted login is considered successful only when the site returns to an allowed high3 URL.
- If the form changes or the site rejects the stored credential, the auth WebView remains visible for manual completion or credential correction; collection state is preserved.

## Runtime stability

- Login routes are rerouted away from the collector before they can replace the active collection document.
- A blocked route does not clear a confirmed high3 session.
- v0.17.5 snapshot-overlap and renderer cooldown protections are retained.
- The auth WebView has its own bounded renderer recreation path.

## Evidence and privacy contracts

- Credentials are never written to source, release assets, diagnostics, SQLite, cloud tasks, URLs, or exported JSON.
- Cookies/session secrets are not exported.
- Jinhak remains user-viewed derived analysis/prediction and is not promoted to official Adiga evidence.
- This release does not infer admission probability; `probabilityInferred=false` remains unchanged.

## Device acceptance

CI verifies source contracts, all unit tests, exact-commit clean rebuild, APK metadata, and the stable signer. Real-device acceptance requires only the normal v0.18.0 run: once credentials have been saved on the device, Jinhak should authenticate without the old high3 confirmation loop and collection should continue after server high3 return.
