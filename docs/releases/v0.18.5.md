# Admission Hub v0.18.5 — Manual Storage Reports

v0.18.5 removes Admission Hub from the Jinhak authentication loop. The app no longer attempts to own, restore, verify, extend, or infer a Jinhak login session. The user signs in and navigates the official Jinhak site directly in the foreground WebView.

## Start condition
Jinhak automation has one start condition: the protected Susi saved-application repository is already visible at `/jh/high3/early/four-year-university/library`.

Before that point Admission Hub does not auto-login, fill credentials, restore an auth lease, run an auth probe, or decide whether login succeeded. Stored Jinhak credentials are cleared from the app credential vault. The browser/provider remains responsible for its own ordinary cookies.

## Application-centric traversal
Once the storage page is visible, the collector does not perform a broad site crawl. It reads the storage cards and promotes only read-only report actions that are structurally bound to the same university/department/application card.

The navigation shape is:

`Susi storage -> one application card -> that application's report -> report lanes/tabs -> return -> next application card`

Eligible report semantics include current prediction, mock-support/applicant distribution, actual-admit/past result, and score-analysis style report controls. Generic search, recommendations, strategy/editorial pages, media, and unrelated Jinhak navigation are not autonomous targets.

If the browser leaves the storage/report scope during a run, the Jinhak batch stops. The user can return to the Susi storage page manually; opening the storage page re-arms the collector.

## Session cleanup
The active Jinhak runtime no longer uses the legacy dedicated `authWebView`, credential autofill, protected-session proof cache, or Jinhak session lease restore. Mission progress may still be persisted so collected report coverage is not lost, but authentication state is not persisted or restored as mission state.

## Evidence safety
The existing evidence boundaries remain unchanged. Jinhak observations are user-viewed/provider-derived evidence, not official evidence. Same-card binding remains required before an application identity is carried into a report. No acceptance probability or unsupported 안정/적정/소신 threshold is inferred.

## Acceptance
CI/unit/APK verification can validate the implementation contract but cannot prove the current Jinhak production DOM. Real Galaxy acceptance should verify: manual login, manual arrival at Susi storage, automatic storage recognition, per-card report traversal, return to storage, and no unexpected generic navigation.
