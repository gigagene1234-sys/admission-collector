# Admission Hub v0.18.4 — Native Jinhak Bridge + Adiga Audit

v0.18.4 keeps the v0.18.3 storage-only Jinhak WebView collector, and adds an optional user-enabled bridge to the installed official Jinhak Android application. It also makes Adiga progress counters explicitly distinguish current-process snapshot attempts from the much larger locally persisted/resumed page plan.

## Jinhak native-app bridge
- The official Jinhak application is targeted as `com.jinhak.jinhakmobile.android`.
- Admission Hub never tries to copy the native app's cookies, login session, tokens, credentials, or form values into its WebView.
- The user explicitly enables the bridge in Android Accessibility settings.
- The bridge is read-only: no clicks, text entry, navigation, or login submission are performed by the accessibility service.
- Password nodes, editable fields, and `EditText` nodes are discarded before any text can be saved.
- Only screens that look like the Susi saved-application repository are persisted to Admission Hub private storage.
- Native-app observations remain `jinhak-user-viewed-native-app` evidence and are never promoted to official evidence.
- Native competition text is preserved as an observation. It is not bound to a university/admission decision unless same-card identity can be verified separately.
- Returning to Admission Hub automatically imports a new fresh native storage observation once.
- If Android reports that the Jinhak package can handle the saved-repository web URL, Admission Hub opens that deep link; otherwise it opens the app's normal launch activity.

## Existing WebView fallback
- The v0.18.3 storage-only WebView path remains available.
- Its Jinhak batch still targets only `/jh/high3/early/four-year-university/library` and keeps the 15-minute storage refresh watch while that run is alive.
- Therefore the native bridge is an additional way to obtain user-viewed storage evidence, not a claim that Android can share the official app's authenticated session with Admission Hub WebView.

## Adiga audit counters
- `attemptedPages` is now explicitly labeled as current-process snapshot attempts, not total known pages.
- The batch summary records the number of logical pages and documents already known/completed at the start of the run.
- `adigaNewCompletedPagesThisRun` exposes the delta produced by the current process.
- The UI completion message displays starting completed pages, current accumulated pages, current-run snapshots, newly completed pages, and unresolved checkpoints.
- Existing Local-First resume behavior is retained: pages already completed in the local SQLite run are not blindly reloaded merely to make the attempt counter look larger.

This explains the previously confusing case where more than 500 logical Adiga pages existed locally while the current process showed only tens of collection attempts. Those are different counters unless a fresh full-audit run is explicitly implemented and requested.

## Evidence policy
- Adiga/university evidence remains official.
- Jinhak WebView/native-app observations remain user-viewed derived evidence.
- No competition observation creates an acceptance probability or 안정/적정/소신 label.
- HOLD and `probabilityInferred=false` behavior remains unchanged.
- Credentials, cookies, session secrets, and editable form values are not exported.

## Real-device boundary
Native-app package/deep-link handling and accessibility tree contents depend on the installed Jinhak app version and the Galaxy device. CI validates the code, privacy boundary, tests, APK signing, and packaging, but real Galaxy acceptance is still required before claiming the native bridge works with the currently installed provider app.
